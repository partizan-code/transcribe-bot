# План реализации Telegram-бота для транскрибации

Дата: 2026-11-09.
Статус: план сохранён; реализация по этому плану ещё не выполнена.

## Запуск реализации в новом чате

Передайте агенту следующий запрос:

> Прочитай применимые AGENTS.md и IMPLEMENTATION_PLAN.md. Реализуй первую версию бота по этому плану, сохраняя существующие локальные изменения. Выполни изолированные тесты без реальных Telegram/AssemblyAI запросов. Допущения и предлагаемые значения из плана используй как исходные настройки, если текущий код не требует корректировки. Не выполняй commit или push. В конце сообщи результат, выполненные проверки и оставшиеся ограничения.

Само сохранение этого документа не является разрешением на реализацию, установку зависимостей, реальные API-запросы, commit или push. Разрешение на реализацию даёт отдельный запрос пользователя, например приведённый выше.

## Согласованные требования

- Бот транскрибирует голосовые сообщения, аудиофайлы и видеофайлы.
- Из видео предварительно извлекается аудио локально.
- Доступ предназначен небольшой группе пользователей.
- Для первой версии достаточно входных файлов до 20 МБ; используется стандартный Telegram Bot API.
- Результат: текст с обозначением говорящих и таймкодами, а также файл SRT.
- Сохраняется плоская структура проекта, Python 3.13, aiogram, AssemblyAI, Loguru и существующий uv workflow.

## Рабочие допущения и предлагаемые настройки

Это предложения из обсуждения, а не отдельно подтверждённые требования пользователя:

- Разрешённые пользователи общаются с ботом в личных чатах. Доступ проверяется по allowlist Telegram user ID из окружения; пустой список не открывает публичный доступ.
- Язык определяется автоматически, разделение говорящих включено. Имена людей не угадываются: используются обозначения «Спикер A», «Спикер B».
- Короткий текст отправляется сообщением; длинный — TXT в UTF-8 с тем же оформлением. SRT прикладывается при наличии распознанной речи.
- Два работника обработки, очередь на десять ожидающих заданий, одно незавершённое задание на пользователя. Лимиты настраиваются.
- Очередь хранится в памяти; после перезапуска незавершённую запись потребуется отправить повторно. Постоянная история и восстановление заданий не входят в первую версию.
- Из видео с несколькими аудиодорожками выбирается первая.
- Максимальную длительность записи и тайм-ауты выбрать и документировать при реализации как настраиваемые ограничения; конкретные значения не согласованы.
- Поддержка video_note («кружков»), групповых чатов, ссылок на внешние записи, оплаты и публичной регистрации не входит в обязательный объём.

## Исходное состояние

По статическому осмотру проекта 2026-11-09:

- `main.py`: создаёт `Bot` и `Dispatcher`, настраивает Loguru, запускает polling. Глобально включён HTML parse mode. Router обработчиков не подключён.
- `handlers.py`: пуст.
- `config.py`: читает `BOT_TOKEN` и `ASSEMBLYAI_API_KEY` через `os.getenv`; задаёт путь к журналу ошибок. `.env` автоматически не загружается.
- `transcribe.py`: синхронный пример обработки `example.mp3` с `language_detection=True` и `speaker_labels=True`. Запрос выполняется при импорте; затем печатается текст и реплики.
- `logger_config.py`: централизованная настройка Loguru, INFO+ в stderr, ERROR+ в `error.log`, диагностический вывод значений переменных отключён.
- `README.md`: пуст. `PROJECT_STATUS.md` отсутствует; не вводить его без отдельного согласования.
- В `uv.lock`: aiogram 3.31.0, assemblyai 1.8.2, loguru 0.7.3. В установленном AssemblyAI SDK найден `assemblyai.prerecorded.v2.AsyncTranscriber`, включая `poll_timeout`, `aclose` и асинхронный context manager.
- Тестовый фреймворк, Ruff и mise tasks в проекте пока не настроены. Не считать их существующими проверками.
- На момент сохранения плана: ветка `main`, upstream отсутствует. Уже изменены `AGENTS.md`, `config.py`, `logger_config.py`, `main.py`; это существующие пользовательские изменения, их необходимо сохранить. В новом чате проверить актуальное состояние заново.

## Архитектура

| Файл | Ответственность |
| --- | --- |
| `main.py` | Создание клиентов и очереди, подключение Router, запуск работников и polling, корректная остановка |
| `config.py` | Валидация настроек, allowlist, лимиты, тайм-ауты, пути к FFmpeg/ffprobe |
| `handlers.py` | Команды, проверка доступа, приём вложений, первичная валидация, постановка заданий |
| `processing.py` — новый | Общий процесс обработки, ограниченная очередь, временные файлы, статусы, управление ресурсами |
| `media.py` — новый | Проверка фактического медиа, длительности и дорожек; извлечение аудио |
| `transcribe.py` | Асинхронная интеграция AssemblyAI и структурированный результат |
| `formatters.py` — новый | Форматирование текста/TXT и построение SRT |
| `logger_config.py` | Существующая единая настройка логирования |
| `tests/test_<module>.py` — новые | Изолированные проверки обработки и форматирования |

Не вводить `src/`, отдельный сервис очередей или базу данных для первой версии. Не помещать всю обработку в Telegram handlers. Возвращаемый результат транскрибации должен сохранять текст, язык, реплики, обозначения говорящих и временные метки слов/реплик, необходимые для SRT.

## Порядок реализации

### 1. Подготовить настройки и жизненный цикл

- Прочитать применимые инструкции и проверить Git, окружение, текущие изменения. Не перезаписывать их.
- Проверять обязательные ключи и allowlist до запуска polling; ошибки не должны содержать секретные значения.
- Выбрать и документировать способ конфигурации: явная загрузка `.env` для локальной разработки либо передача переменных окружения. При загрузке `.env` не переопределять уже заданное окружение.
- Новые прямые зависимости, если нужны, объявлять через uv и согласованно обновлять lockfile. Не мигрировать toolchain.
- Проверять наличие FFmpeg/ffprobe и выдавать понятную диагностику, если обработка видео недоступна.
- Создавать и закрывать клиенты Telegram и AssemblyAI в управляемом жизненном цикле; при остановке завершать работников и дочерние процессы, очищать ресурсы.

### 2. Превратить transcribe.py в библиотечный модуль

- Убрать запросы, чтение аудио и печать результата при импорте. Если самостоятельный пример сохраняется, запускать его только под `if __name__ == "__main__"`.
- Реализовать асинхронную транскрибацию через доступный `AsyncTranscriber` и структурированный результат с аннотациями типов.
- Сохранить определение языка и разделение говорящих.
- Обрабатывать ошибки SDK/сервиса, пустой текст и отсутствующие реплики/временные метки.
- Ограничить сетевые операции и общее ожидание результата. Не считать локальный тайм-аут гарантией отмены задания у провайдера.
- Не создавать повторное платное задание автоматически при неизвестном результате предыдущей отправки. Повторное получение статуса уже созданного задания отличать от повторной отправки на транскрибацию.

### 3. Реализовать голосовые сообщения от начала до конца

- Добавить Router, `/start`, `/help`, обработчик `voice` и подключить их в `main.py`.
- Проверять доступ, размер, ограничения пользователя и вместимость очереди до скачивания и платных операций.
- Постановку задания и учёт активного задания пользователя сделать согласованными, без гонок. При отказе/ошибке освобождать резервирование.
- Ограничить очередь через `asyncio.Queue`, запускать фиксированное число работников. При заполнении сообщать о занятости, не накапливать неограниченное число ожидающих задач.
- Скачивать через aiogram в отдельный временный каталог задания. Использовать внутренние имена файлов, не строить пути из пользовательского имени.
- Проверять заявленный и фактический размер. Учесть отсутствие метаданных; ограничить объём скачивания и время операции.
- Реализовать цикл: проверка → очередь → скачивание → проверка медиа → транскрибация → форматирование → доставка → очистка.
- Удалять временные входы и результаты после доставки, ошибки или отмены, закрывая файловые дескрипторы до удаления, в том числе на Windows.

### 4. Подключить аудиофайлы и документы

- Обработать `audio` и аудио, отправленное как `document`, через тот же процесс.
- Расширение и MIME использовать только для предварительного отбора. После скачивания проверять реальное содержимое и длительность.
- Явно описать поддерживаемые форматы; неподдерживаемые и повреждённые файлы отклонять понятным сообщением.
- Не перекодировать совместимое аудио без необходимости. Проверять совместимость с выбранным API/моделью по актуальной документации при реализации.

### 5. Добавить видео

- Обработать `video` и видео, отправленное как `document`.
- Через ffprobe определить длительность и наличие аудиодорожки. Отсутствие звука — отдельный ожидаемый результат.
- Через FFmpeg извлечь первую аудиодорожку в документированный формат, подходящий AssemblyAI. Не обрезать начало или паузы так, чтобы нарушить соответствие таймкодов исходному видео.
- Запускать subprocess асинхронно, списком аргументов и без shell. Ограничить время и ресурсы обработки; при тайм-ауте/отмене завершить процесс и дождаться его выхода.
- Входами считать локальные файлы; не разрешать медиаобработчику неожиданно скачивать внешние ресурсы из вложенных ссылок/плейлистов.
- Использовать переносимые пути; FFmpeg и ffprobe описать как системные зависимости отдельно от Python-пакетов.

### 6. Оформить текст и SRT

Пример текстового результата:

```text
[00:00:03] Спикер A:
Давайте обсудим результаты.

[00:00:08] Спикер B:
Первый этап завершён.
```

- Короткий результат отправлять сообщением; превышающий лимит Telegram — файлом TXT в UTF-8 с кратким уведомлением.
- Для транскрипта явно отключать `parse_mode` либо корректно экранировать текст. Глобальный HTML из `main.py` не должен менять или ломать распознанный текст.
- SRT: последовательные номера блоков, интервалы `HH:MM:SS,mmm --> HH:MM:SS,mmm`, текст с обозначением говорящего и пустая строка между блоками.
- Формировать SRT из структурированных данных, чтобы сохранить говорящих. Длинные реплики разбивать на читаемые блоки по временным меткам слов; не придумывать точные временные метки делением строки на равные части.
- Проверять валидность и хронологический порядок интервалов, положительную длительность блоков. Учитывать реальное перекрытие речи, не сдвигая автоматически всю временную шкалу.
- Если нет метки говорящего, использовать нейтральное обозначение. Если нет данных для корректного SRT, доставить доступный текст и явно сообщить об ограничении, не выдавая вымышленные таймкоды.
- Если речь не обнаружена, сообщать об этом без пустых TXT/SRT.

### 7. Статусы, ошибки и журналирование

- Редактировать одно служебное сообщение: «В очереди», «Скачиваю», «Извлекаю аудио» для видео, «Распознаю», затем результат либо понятная ошибка. Не показывать выдуманный процент выполнения.
- Различать отказ в доступе, превышение лимитов, заполненную очередь, повреждённое медиа, отсутствие аудио/речи, недоступность FFmpeg, сетевую ошибку, тайм-аут и ошибку доставки результата.
- Ошибка одного задания не должна останавливать работника или polling.
- Если транскрибация завершена, но отправка результата не удалась, не запускать новую транскрибацию ради повторной доставки. Повторы доставки ограничить.
- Использовать существующий Loguru. Логировать идентификатор задания, этап, длительность и безопасное описание ошибки; не логировать ключи, URL с токеном, содержимое медиа или транскриптов.
- В `/help` и README объяснить передачу записи в AssemblyAI. Локальная очистка не означает удаления данных у провайдера; не обещать этого без отдельной реализации.

### 8. Проверки и документация

- Добавить тесты в `tests/` с заглушками Telegram и AssemblyAI, временными файлами и тестовыми настройками без загрузки реальных секретов.
- Сначала проверить форматирование и общий процесс, затем обработчики, очередь и ошибки. Тесты не должны обращаться к внешним сервисам.
- Покрыть: голосовое, аудио, видео и document; отказ в доступе; лимит размера и отсутствие метаданных; ограничение длительности; переполнение очереди; повторное задание пользователя; повреждённый файл; видео без звука; пустой результат; отсутствие говорящих; ошибку и тайм-аут сервиса; длинный текст; HTML-символы; смену говорящих; разбиение SRT; очистку ресурсов и освобождение пользовательского лимита при ошибках/отмене.
- При наличии FFmpeg выполнить локальную интеграционную проверку на небольшом синтетическом медиа во временном каталоге, без реальной записи пользователя. Проверить извлечение и сохранение временной шкалы. Если инструмента нет, сообщить об ограничении проверки.
- Заполнить README: настройка окружения, allowlist, FFmpeg/ffprobe, запуск, тесты, поддерживаемые форматы, лимиты, формат результата, потеря очереди при перезапуске и обработка данных внешним провайдером.
- Добавить `.env.example` с пустыми/фиктивными значениями. Не читать и не публиковать секреты из пользовательского `.env`.
- При изменении Python выполнить доступные релевантные Ruff-проверки. Если инструмент недоступен, явно сообщить; не утверждать, что проверки прошли.
- Проверить итоговый diff и статус Git. Без отдельного разрешения не выполнять staging, commit или push.

## Критерии готовности первой версии

- Разрешённый пользователь может передать каждый из трёх типов медиа в пределах ограничений и получить расшифровку с говорящими/таймкодами и корректный SRT при наличии речи и временных данных.
- Аудио/видео, отправленные документом, проходят тот же процесс обработки.
- Для видео в AssemblyAI передаётся предварительно извлечённое аудио.
- Долгая обработка не блокирует ответы бота другим пользователям; очередь и число одновременно обрабатываемых заданий ограничены.
- Пользователь получает понятные статусы и ожидаемые ошибки.
- Длинный результат доставляется TXT; содержимое транскрипта не интерпретируется как HTML.
- Нет сетевых вызовов при импорте модулей, утечек временных файлов при штатном завершении/ошибках или незакрытых процессов FFmpeg.
- Изолированные тесты проходят; непроверенные реальные интеграции и особенности окружения явно перечислены в отчёте.
- Документация позволяет настроить и запустить проект в новом окружении. Реальные API-проверки выполняются только по отдельному разрешению пользователя на конкретную операцию.

## Источники и ограничения

Документация просмотрена при планировании 2026-11-09; при реализации проверить актуальность API и совместимость с зафиксированными версиями:

- Telegram getFile и лимит скачивания 20 МБ: https://core.telegram.org/bots/api#getfile
- Собственный Telegram Bot API server для будущей поддержки больших файлов: https://core.telegram.org/bots/api#using-a-local-bot-api-server
- Лимит обычного сообщения 4096 символов: https://core.telegram.org/bots/api#sendmessage
- Скачивание через aiogram: https://docs.aiogram.dev/en/latest/api/download_file.html
- Официальный Python SDK AssemblyAI: https://github.com/AssemblyAI/assemblyai-python-sdk
- FFmpeg: https://ffmpeg.org/ffmpeg.html

Сжатие/извлечение аудио после скачивания не обходит ограничение Telegram на размер исходного видео. Для файлов больше 20 МБ понадобится отдельный этап инфраструктуры, который не входит в этот план. Число байт для прикладного лимита необходимо явно определить в конфигурации с учётом ограничения API.

При планировании приложение и тесты не запускались, реальные API не вызывались. Качество распознавания, определения языка и разделения говорящих на реальных записях пока не проверено.
