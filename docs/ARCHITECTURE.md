# Архитектура

Приложение работает одним процессом с polling aiogram и очередью в памяти.
Схема успешного пути задания приведена в [README](../README.md#архитектура).
Базы данных, внешнего брокера, постоянной истории и восстановления заданий нет.

## Ответственность модулей

| Модуль | Ответственность |
| --- | --- |
| [main.py](../main.py) | Настройка Loguru, проверка инструментов, создание клиентов, Router и JobManager, запуск и остановка. |
| [config.py](../config.py) | Чтение `.env` и окружения, константы приложения. |
| [handlers.py](../handlers.py) | Проверка доступа, команды, первичная проверка метаданных, резервирование места. |
| [processing.py](../processing.py) | JobManager, очередь, workers, скачивание с лимитом, доставка и очистка задания. |
| [media.py](../media.py) | Проверка содержимого и подготовка аудио через локальные subprocess. |
| [transcribe.py](../transcribe.py) | AsyncClient/AsyncTranscriber AssemblyAI, ожидание результата и нормализация моделей. |
| [formatters.py](../formatters.py) | Текст с говорящими и временем, построение SRT. |
| [errors.py](../errors.py), [logger_config.py](../logger_config.py) | Ожидаемые ошибки и общая настройка журналирования. |

`transcribe.py` при импорте не создаёт SDK-клиент и не делает сетевых запросов.
Клиент создаётся в `TranscriptionService`, запрос — в его методе `transcribe()`.

## Допуск и очередь

1. `handlers.authorized()` проверяет личный чат, наличие отправителя, отсутствие
   признака бота и вхождение user ID в allowlist.
2. `attachment_from_message()` выбирает `voice`, `audio`, `video` или `document`,
   предварительно проверяет тип документа, заявленные размер и длительность.
3. `JobManager.reserve()` проверяет остановку, активное задание пользователя
   и вместимость: `queue.qsize() + len(reservations) < QUEUE_SIZE`.
4. После отправки статуса «В очереди» `enqueue()` помещает `Job` в `asyncio.Queue`
   через `put_nowait()`. При ошибке или отмене до постановки резервирование снимается.

Изменения допуска выполняются без `await` в одном event loop. Резервирование
учитывает время отправки статуса и не даёт параллельным обработчикам превысить
лимит ожидающих заданий. Активные workers учитываются отдельно: настройки задают
10 ожидающих/зарезервированных и до 2 обрабатываемых заданий. Пользователь остаётся
в `active_users` до завершения всего задания, включая доставку.

## Обработка и жизненный цикл

Фиксированный pool задач `asyncio` получает задания из очереди. Для каждого задания:

1. Создаётся `TemporaryDirectory` с внутренними именами `input.media` и `audio.wav`;
   пользовательское имя файла не используется как путь.
2. Выполняются `get_file` и скачивание с проверкой заявленного и фактического размера.
   `LimitedWriter` отклоняет запись очередного блока при превышении лимита.
3. ffprobe проверяет дорожки и длительность. Для обнаруженного видео или вложения
   Telegram типа `video` FFmpeg извлекает первую аудиодорожку; результат проверяется снова.
4. AssemblyAI получает аудио с `language_detection=True` и `speaker_labels=True`.
   SDK ожидает завершение отправленного задания; результат нормализуется в `Transcript`.
5. Формируются и доставляются текст/TXT и доступный SRT. Временный каталог закрывается.
6. В `finally` worker освобождает пользователя и вызывает `queue.task_done()`.

Клиенты и subprocess используют асинхронный I/O. Ошибки задания обрабатываются
в worker и не завершают его цикл. `close()` запрещает новый допуск, отменяет
workers, ожидает их, удаляет ожидающие элементы очереди и очищает учёт пользователей.
Остановка не сохраняет и не переносит задания на следующий запуск.

В `main()` бот находится в асинхронном контексте, а при выходе из polling
последовательно закрываются JobManager и сервис транскрибации. Подробнее о
локальной очистке и удалённом задании — в [OPERATIONS.md](OPERATIONS.md).

## Данные и форматы результата

`Transcript` хранит общий текст, язык, реплики `Utterance` и слова `Word`.
Временные метки задаются в миллисекундах; при нормализации отрицательные,
нецелые и булевы значения превращаются в `None`. Реплики имеют приоритет;
если их нет, слова объединяются по последовательным группам говорящих.

### Текст и TXT

`format_text()` оформляет реплику как `[HH:MM:SS] Спикер A:`, затем перевод
строки и текст; между репликами — пустая строка. Миллисекунды в текстовом
таймкоде опускаются. Без начала реплики префикс времени отсутствует, без
говорящего используется «Спикер». Если реплик/слов нет, возвращается общий текст.

При длине до 4096 единиц UTF-16 результат отправляется сообщением, иначе —
`transcript.txt` в UTF-8. В обоих случаях `parse_mode=None`: HTML в транскрипте
не интерпретируется. Пустой текст приводит к статусу «Речь не обнаружена.» без файлов.

### SRT

`format_srt()` принимает только интервалы с `0 <= start < end`. При корректных,
упорядоченных по началу метках слов новый блок начинается перед словом, если:

- добавление слова превысит 72 символа текста или длительность 6000 мс;
- пауза после предыдущего слова больше 1500 мс;
- меняется говорящий.

Это границы группировки, а не гарантия длины любого блока: отдельное длинное
слово не разрезается. Если метки слов непригодны или отсутствуют, но интервал
реплики корректен, используется вся реплика с её исходным интервалом.
Время не выводится из количества символов; длинная реплика без меток слов
не разбивается на вымышленные временные интервалы.

Блоки сортируются по началу и затем концу; перекрытие речи сохраняется.
Нумерация начинается с 1, время записывается как `HH:MM:SS,mmm`, между блоками
пустая строка. Пробелы текста нормализуются, `-->` в тексте заменяется на `→`.
Подпись «Спикер …:» и текст переносятся с целевой шириной 42 символа без разрыва
длинных слов. Синтетический пример — в [README](../README.md#демонстрация-результата).

Результат `Subtitles` содержит текст и флаг `incomplete`: непригодные реплики
пропускаются; при отсутствии пригодных блоков SRT не отправляется. Пользователь
получает доступный текст и пояснение об ограниченных или отсутствующих субтитрах.
